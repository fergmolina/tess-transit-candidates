## Remaining required corrections

### 1. Bind the scored result to the actual clock JSON, and fail closed on missing hashes

The new validator checks the clock's declared config/prior identity, then the result's config/evaluator identity and LC-hash equality. It never compares **`result.clock_record.sha256` with the SHA-256 of `--clock`** (`validate_round4_inputs.py:26–37`). The unchanged evaluator already records that actual input-artifact hash at `prereg_conformance.py:229`; it is available for this check.

I constructed two synthetic clock JSONs with identical TIC, sector, config, prior, prediction and LC identity fields, but corrections of **0.1 and 99.9 min**. A synthetic evaluator result explicitly identified the second clock's hash; I supplied the first clock to the validator. The result-stage validator returned **exit 0, BOUND**. It also returned BOUND after removing `clock_record` completely, and after removing both `result.lc_sha256` and `clock.qlp_sha256` (because `None == None`). These are metadata-only refusal probes; they do not claim that a real scientific RECOVERED outcome was generated. Evidence: `/tmp/round4_recheck2/binding_probe.py`, `.log`, and `probe/*.json`.

**Exact fix:** for a result that reached clock-dependent scoring, require nonempty, correctly formed SHA-256 strings and require `e['clock_record']['sha256'] == sha(a.clock)`, in addition to the existing config/evaluator/prior and LC checks. Require the two LC hashes to exist and be valid before comparing them. Add independent refusal cases for a different clock artifact with the same config/LC but changed corrections, missing clock provenance, missing/malformed LC hashes and changed evaluator identity. The current positive synthetic result at `test_round4_configs.py:52` omits `clock_record`, so change that fixture to model a genuinely bound scored result.

Handle early refusals/INSUFFICIENT outputs explicitly: the evaluator can return before the clock gate (`prereg_conformance.py:223`). Such outputs may legitimately lack `clock_record`; classify them as pre-clock outcomes rather than silently certifying clock-dependent scoring. Preserve the pinned evaluator and S106 files; the fix belongs in the new wrapper and its tests. Update the wrapper docstring/mandatory note to say the scored output is bound to the **same clock record**, not merely the same light curve.

The current pre-stage does correctly enforce the locked config bytes, canonical prior path and prior bytes, prediction bytes and pinned evaluator (`validate_round4_inputs.py:17–25`). All eight manifest entries currently match their config/prior files; the manifest SHA is `d7a20a59cccbf8bf1908ba57cb4bc2447a674b1901359abfd9ed727b32c5ade3`, agreeing with the amended registrations. This is a remaining final-stage binding defect, not a failure of those successful checks.

2. **Make the ground precision calculation's units and approximation explicit.** `3367979/PREREGISTRATION_v4.md:9` gives the right rounded result but leaves the mag-to-mmag factor implicit. Write “`1000 × 1.0857 × 0.000788 × sqrt(7.8) / 4 = 0.597 mmag ≈ 0.6 mmag`, an ideal white-noise estimate before baseline/shape losses.” At exactly 0.6 mmag this ideal expression gives SNR 3.982, approximately 4; the measured per-epoch SNR ≥4 requirement remains necessary. A precision requirement “≤1.5 mmag” does not literally make recovery unreachable, because it also permits better precision; say “at 1.5 mmag the reference transit would have ideal SNR ≈1.59.” No new freeze is needed to clarify this approximation. Arithmetic reproduced in `/tmp/round4_recheck2/all_hashes.py`; ground outcome text is at registration:142.
3. **Move the missing-predecessor refusal before writes.** The new introduction branch is correct, but its no-earlier-v2+ refusal at `prereg_v2.py:147` occurs after CSV and JSON writes at lines 139 and 141. An invalid future version request could therefore leave partially frozen outputs and block a corrected retry. Validate the requested predecessor before those writes. This is a source-level observation, not a test that wrote any project file; it does not invalidate the correctly generated 3367979 v4.
